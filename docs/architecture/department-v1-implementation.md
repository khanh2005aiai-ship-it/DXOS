# Department V1 implementation — DXOS-DOMAIN-003

Pre-migration review: Department already has organization FK, unique (organizationId,code), unique (organizationId,id), and tenant-constrained optional parent FK/index. Preserve all existing columns, codes and parent relationships. Add nullable VARCHAR(1000) description and ACTIVE/INACTIVE enum status default ACTIVE only. No new index: existing organization/id key supports keyset pagination; status filtering uses that bounded tenant scan until measured needs justify another index.

Planned additive migration: 20260909000000_department_v1. Existing records receive ACTIVE/null without code normalization or parent changes. MySQL 8.0.44 / Prisma 6.19.3 stay fixed. Replay the full history in disposable test/shadow databases and compare schema. No historical migration edits. Before any canonical database deployment inspect current migration status and schema; reject unexpected drift. Rollback application exposure first; retain additive columns/data. Dropping the new columns is a separate destructive operation requiring a backup and explicit approval, not an automatic down migration.

The implementation brief explicitly asks for a Department module. Use DepartmentsModule with DepartmentsService, as a cohesive unit inside the modular monolith; this replaces DOMAIN-002's suggested placement inside OrganizationsModule, without changing ownership or introducing a service boundary. It imports existing IAM/RBAC/AuditWriter and uses owned Department rows. No Employee, Task, notification or hierarchy functionality.

All operations recheck authorization in serializable transactions. Updates explicitly select tenant plus ID. New permissions are catalog entries only; owner bootstrap remains unchanged. Audit department.created/updated joins the write transaction and permits only bounded field-name metadata; legacy event allowlists remain unchanged. No-op updates preserve updatedAt and emit no audit. Description/status/name changes never change code or parent.

Deployment verification (2026-09-09): local dx_os was MySQL 8.0.44, with eight successfully applied checksum-matching migrations, no drift against the pre-change schema and zero Department rows. Applied only 20260909000000_department_v1 using Prisma migrate deploy. Status reports all nine migrations applied; live columns are nullable varchar(1000) description and non-null enum('ACTIVE','INACTIVE') status default ACTIVE. Full live schema comparison reports no difference. Existing keys/parent column remain. Prisma Client is 6.19.3. Replay and shadow comparison use uniquely named disposable databases, never reset dx_os.

HTTP body parsing uses the existing Nest Express adapter: a Department-scoped 64 KiB decoded JSON parser precedes the normal default JSON parser, preserving other endpoint limits. Parser errors use the safe error envelope/requestId. Raw gzip/chunked and case-insensitive route tests cover the limit; malformed transport is rejected before guards. Valid JSON follows existing JWT/tenant guards and strict DTO validation. The test runner now forwards explicit Jest selection arguments so targeted Department tests and the default complete suite share the same isolated migration setup.

Known limits: no hierarchy writes/deletion, Employee/Task integration, private department ACL, default role grants, or provisioning UI. New grants require explicit trusted provisioning through existing RBAC mechanisms; deployment alone grants no user access. Inactive departments remain readable and retain historical references. Future referencing services must implement active-reference validation under the same transactional boundary before shipping.
