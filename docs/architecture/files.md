# Secure file foundation

Organization files require explicit file:upload/read/delete grants through existing IAM/RBAC. Uploader identity is provenance, not a private-file ACL or automatic grant. No default owner/admin grants. Every metadata/download/delete lookup includes the route tenant; invalid/foreign IDs return 403. JWT and permission guards precede multipart parsing; service transactions recheck authorization.

The additive file_objects table uses UUIDs, DATETIME(6), a composite uploader-membership FK with restrictive deletion, and a unique opaque storage key. The membership-prefix index supports the FK; primary-key lookup plus tenant/status predicates serves the only read pattern (no list API). No speculative list indexes. Size and SHA-256 are null until streaming completes; storage provider is LOCAL. Original filename is display-only, limited to 200 ASCII safe characters, rejecting traversal, separators, encoded paths, controls and absolute names. No user-controlled physical paths.

UPLOADING is reserved in MySQL before writing bytes. Storage streams and computes authoritative size, SHA-256 and an initial signature. After valid multipart completion, AVAILABLE and file.uploaded audit commit together. Storage failure, parser failure, disconnect, or database finalization failure invokes compensation: commit FAILED before deleting the opaque object. If storage cleanup fails the record remains FAILED with its key retained for retry; if the database is unavailable it may remain UPLOADING. Both states are inaccessible. A database commit whose result is uncertain must be re-read: never delete an AVAILABLE object. Internal cleanupUpload(id) can be retried on an abandoned reservation only after confirming the original request is no longer running. No automatic crash recovery/scheduler is added. Operators must review interrupted UPLOADING rows after restart; this is not a filesystem/database distributed transaction.

DELETE atomically marks AVAILABLE as DELETED with file.deleted audit, preserves metadata and bytes, and is idempotent. There is no permanent-delete API or retention policy. Downloads authorized before a concurrent delete may finish; new requests cannot download deleted objects. No notifications are generated.

StorageService abstracts put/get/delete/exists. Local storage is lazy, defaults to ~/.dx-os/files, and accepts absolute FILE_STORAGE_ROOT configuration. It must be private, outside public/static hosting, and owned by the backend process; no other writer is supported. Existing symlinks/junctions in path components and object links are rejected. UUID-only flat keys, exclusive creation and bounded streams prevent path traversal and overwrites. Administrators who can race-replace the root or modify process-owned files remain outside application protection. No provider credentials or paths enter responses/audits. Local filesystem data and metadata must be backed up together.

Exactly one multipart field named file, no text fields; nonempty, maximum 5 MiB. Allowed declared MIME must match basic PDF/PNG/JPEG signature; signature matching is not complete format validation or malware detection. Extensions are not trusted. Files are always attachment downloads with nosniff and private no-store caching. No execution, static hosting, public URLs, antivirus, deduplication, or external provider. SHA-256 is server-calculated and returned for integrity comparison; no cross-tenant deduplication.

Migration 20260907040000_file_objects creates an empty table; no existing rows/history change. Rollback requires disabling file routes, exporting metadata and preserving associated storage before an explicitly approved table removal. Never edit historical migrations. The new grants are catalog entries only; trusted provisioning must create the permission catalog rows before the existing RBAC assignment service grants them.
