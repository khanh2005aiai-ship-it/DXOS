# Task planning additions — DXOS-FEATURE-EXPANSION-001

Documented before implementation. Base T = /api/v1/organizations/:organizationId/tasks/:taskId. Additive operations; existing Task JSON, status lifecycle and permission matrix remain unchanged.

All operations require authenticated ACTIVE user/session/organization/membership and the stated existing permission. Every lookup and mutation is scoped to organization AND task; authorization repeats inside the serializable transaction. Existing 401/403/404/409/400/413/500 error envelope applies. Foreign and missing child resources are indistinguishable 404. Unknown body/query fields, client ownership/permissions and malformed IDs are rejected. JSON mutations retain the decoded 64 KiB maximum.

- GET T/planning: task:read. Returns `{reviewer,checklist}`. reviewer is null or `{employeeId,displayName}`; displayName is null unless the caller also has employee:read. checklist is the full, bounded list (maximum 100 items per task), ordered createdAt/id ascending. Item `{id,taskId,title,isCompleted,createdAt,updatedAt}`. No actor/security/internal fields.
- PATCH T/planning/reviewer: task:assign. Strict `{reviewerEmployeeId: UUID|null}`. Non-null reviewer must be an eligible ACTIVE same-organization Employee/User/membership using EmployeesService. Returns `{employeeId,displayName}` or null with the same name-read rule. No new implicit task permission or role grant. Reviewer designation is informational at this stage; it does not impose a new completion gate or imply an approval decision. Future approval workflows must define their own transitions. Same value is idempotent.
- POST T/checklist: task:update. `{title:string}` trimmed 1..200, no control characters. Returns 201 item, initially incomplete. Reject a 101st item with 409.
- PATCH T/checklist/:itemId: task:update. Nonempty subset `{title,isCompleted:boolean}`; strict boolean. Returns 200 item. No-op preserves updatedAt and audit.
- DELETE T/checklist/:itemId: task:update. Empty/no JSON body and no query; returns 204. Repeated missing delete returns 404.
- GET T/activity: task:read. `{items,nextCursor}`; limit 1..100/default25, after UUID, ordered createdAt descending then id descending. Cursor lookup is scoped to this task, organization and event allowlist; foreign/missing cursors both return 400. Only allowlisted Task mutation events with resourceType task and matching task ID are projected as `{id,event,createdAt}`. No audit metadata, actors, comments, files, IAM/security events or foreign resources. Existing child comment/file events whose resource ID is the child remain in their own collections and privileged audit log, not falsely attributed to a task. No success-read audit.

DONE/CANCELLED reject reviewer writes and all checklist mutations. Reads remain possible. Checklist completion does not change Task progress/status or imply nested Tasks. Parent Tasks have independent progress and optional reviewer; preserve existing completion behavior. No recursive hierarchy or duplicate Task model.

New atomic audit events `task.checklist.added`, `task.checklist.updated`, `task.checklist.removed` and `task.reviewer.changed` have resourceType task, Task ID and empty metadata. No checklist titles, IDs of other users, field values or comment text are logged. Mutation grants may return the safe mutation response without requiring task:read, consistent with Work.

Kanban UI groups the current filtered Task query and uses existing PATCH status semantics; each status column pages independently so a first-page subset is never shown as the entire organization board. It offers accessible status actions; completed/cancelled cards cannot be dragged back into open states. No silent reordering persistence or new status enum.
