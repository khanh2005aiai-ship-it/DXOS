# Notification API v1 (additive) — DXOS-NOTIFY-001

## Notification Center extension — DXOS-FEATURE-EXPANSION-001

Recorded before implementation. No schema, migration, dependency or new permission. Preserve ACTIVE user/session/organization/membership and authenticated recipient scoping for every query/update; never accept recipient/tenant overrides. Successful reads and read-state changes remain unaudited under existing policy.

- Existing GET list adds optional `category=work|organization|other`. work maps to task.assigned, organization maps to organization.updated, other captures any remaining stored type. No fake notifications or new event producers. Category and read-state filters combine; cursor remains tenant/recipient scoped independent of filters, with existing chronological ordering.
- GET `/api/v1/organizations/:organizationId/notifications/summary`, strict empty query: `{total,unread,read,categories:{work:{total,unread},organization:{total,unread},other:{total,unread}}}`. Exact persisted counters across all pages, in one serializable transaction. No notification bodies, IDs, other recipients or organization-wide aggregate.
- PATCH `/api/v1/organizations/:organizationId/notifications/read-all`, absent body or `{}`, strict empty query: `{updatedCount:number}`. Atomically mark all unread notifications for the current recipient in this organization, irrespective of UI category/filter. Preserve all existing readAt values and message contents. Repeat returns updatedCount0; new notifications committed after the operation remain unread. Existing error envelope:401 authentication,403 inactive/foreign organization membership,400 extra body/query fields,409 conflict,500 persistence error. No read-all route accepting an arbitrary recipient.

Frontend shows exact unread count, category/read-state filters and explicitly labeled bulk action across all categories. Mutation errors remain visible; no silent failures or fabricated counts on network errors. Refresh the organization-bound header count after successful mutations. No permission grants, credential updates or external delivery.

GET `/api/v1/organizations/:organizationId/notifications` returns `{items: Notification[], nextCursor: UUID | null}`. Query: limit integer 1–100 (default 25), after UUID, optional state `read` or `unread`. Unknown fields including recipient/user/organization overrides return 400. Ordering is createdAt DESC, id DESC; after must reference this tenant and recipient. Cursor validity does not depend on its current read state. Pages reflect live changes, not a historical snapshot.

PATCH `/api/v1/organizations/:organizationId/notifications/:notificationId/read` accepts an absent body or `{}` and returns Notification. Other body fields return 400. Repeated calls preserve the first readAt. Only readAt changes.

Notification: id, organizationId, recipientUserId (UUID); type (`organization.updated` or `task.assigned`); title (1–200), body (1–1000) server-defined text; metadata (object, <=1024 UTF-8 bytes, type-specific: organization.updated permits optional changedFields exactly `["name"]`; task.assigned requires only taskId UUID); createdAt (ISO timestamp); readAt (ISO timestamp or null); isRead (readAt != null).

Bearer JWT required. Missing/invalid/expired or inactive identity: 401. Active organization membership is required: 403 for invalid/nonmember/inactive tenant or foreign/missing notification IDs. Reading own notifications requires no administrative RBAC grant. There is no cross-tenant aggregate inbox; multi-organization users choose the organization route explicitly. Header/body tenant or recipient values cannot override authenticated ownership. Invalid query/cursor/body: 400; exhausted transaction conflict retries: 409; operational failure: 500. Errors use the existing ErrorResponse envelope and request correlation.

No public creation, delete, content edit or admin inbox route. Organization update authorization is unchanged. An authorized organization name update creates one confirmation for the actor in the same transaction with notification.created audit. Reads are not audited. This adds APIs without changing existing response contracts or requiring frontend changes. OpenAPI served by the existing documentation endpoint is the machine-readable contract.
# Task V1 assignment extension — DXOS-DOMAIN-005

The catalog additionally supports task.assigned with fixed title `Task assigned`, body `A task was assigned to you.`, and required sole metadata `{taskId: UUID}`. The existing organization.updated metadata policy is unchanged. New non-self assignment/reassignment notifies only the same-tenant eligible Employee's User. Suppress unchanged/self/unassigned/ordinary edits. Task, notification and audits share the mutation transaction; failure rolls back all. Repeated identical PATCH is a no-op, not a second notice. The notice grants no task:read access. Existing recipient-owned list/read routes are unchanged; no new public creation or delivery infrastructure.
