# File API v1 — DXOS-FILES-001

All routes require bearer JWT, active user/organization/membership and explicit tenant RBAC grants. No automatic owner/admin grant; these are organization-shared files, not user-private files. Uploader identity records provenance. No storage paths, keys or provider details appear in responses. Existing contracts are unchanged; these routes are additive.

POST `/api/v1/organizations/:organizationId/files`: file:upload. Exactly one multipart file part named `file`, no other fields. Maximum 5,242,880 bytes, nonempty. Declared MIME must be application/pdf, image/png or image/jpeg and match the basic signature. Extensions are not authoritative; this is not complete format validation or antivirus. Filename: 1–200 characters, ASCII letters/digits/spaces/periods/underscore/hyphen, starts alphanumeric, no `..`, trailing period/space, separators, percent escapes, controls or absolute path. Filename is display-only. Returns 201 FileMetadata after storage, metadata and upload audit succeed. Size and SHA-256 derive from streamed bytes; no client size, checksum, uploader, tenant or key fields accepted.

GET `/api/v1/organizations/:organizationId/files`: file:read. Returns `{items:[FileMetadata],nextCursor:UUID|null}` using ascending ID keyset pagination (`limit` 1–100, default 25, optional `after`). Only `AVAILABLE` files in the requested organization are returned; `UPLOADING`, `FAILED` and `DELETED` rows are excluded. The cursor is an exclusive tenant-scoped lower bound, not an authorization token. Unknown query fields and malformed values return 400.

GET `/api/v1/organizations/:organizationId/files/:fileId`: file:read. Returns 200 FileMetadata for AVAILABLE file only.

GET `/api/v1/organizations/:organizationId/files/:fileId/content`: file:read. Streams binary bytes with validated Content-Type, Content-Length, Content-Disposition attachment, X-Content-Type-Options nosniff, Cache-Control private,no-store. No public URLs or arbitrary storage-key route.

DELETE `/api/v1/organizations/:organizationId/files/:fileId`: file:delete. Empty/absent body only. Returns 200 FileMetadata with DELETED; repeated deletion preserves timestamp and does not duplicate audit. Metadata and bytes are retained; future reads are denied. An already-authorized download may finish.

FileMetadata: id, organizationId, uploadedByUserId (UUID), originalFilename (bounded string), contentType (allowlisted MIME), size (server byte count), checksum (server SHA-256 lowercase hex), status (AVAILABLE or DELETED on successful public responses), createdAt/updatedAt (ISO timestamps). Listing returns only AVAILABLE metadata. No storage key, filesystem path, provider detail or credentials are returned. All other body/query fields are rejected. Tenant context is the existing route parameter and is checked server-side.

Errors use existing ErrorResponse with requestId: 400 malformed multipart/missing file/unsafe filename/extra fields; 401 invalid/missing/expired/revoked credentials or inactive user; 403 nonmember, inactive tenant/membership, missing permission, inaccessible/foreign/invalid file ID or unavailable lifecycle; 413 oversized upload; 415 unsupported MIME/signature; 409 exhausted transaction conflicts; safe 500 database/storage/cleanup failure. File contents and physical paths are never returned in errors or audit records.

UPLOADING metadata is reserved before storage, AVAILABLE + file.uploaded audit commit atomically after successful streaming and multipart validation. Failures atomically transition to FAILED before cleanup of bytes; cleanup failure retains a retryable FAILED record. Uncertain database results are rechecked before compensation; AVAILABLE data is never compensated. Crash/interrupted UPLOADING records require internal cleanup after confirming the old request has stopped. No distributed transaction is claimed. See docs/architecture/files.md for operations and limitations. No per-file notifications.
