# Dashboard — DXOS-FEATURE-EXPANSION-001

Additive GET `/api/v1/organizations/:organizationId/dashboard`. Valid JWT/session and ACTIVE user, organization and membership required. No query parameters or request body are supported. Unknown query parameters return 400. Invalid/inaccessible organization returns 403; invalid authentication returns 401. No entity lookup or 404 case. Operational errors remain errors, never synthetic zero counts.

Return `{organizationId,generatedAt,tasks,departments,employees,workload,notifications,activity}`. Each section is independently authorized from effectivePermissions inside one serializable transaction. No new privilege, role-name bypass or automatic grant. Unauthorized sections are null; authorized empty counters are zero and empty ratios are null. Client-provided permissions are rejected.

- tasks (task:read): `{total,byStatus:{TODO,IN_PROGRESS,DONE,CANCELLED},open,overdue,unassigned,completionPercent,health,overdueItems,overdueHasMore}`. All counters cover the full organization, not a page. Open = TODO + IN_PROGRESS. Overdue = open with dueAt strictly before generatedAt. Unassigned = open with null assignee. Completion = DONE / (total - CANCELLED) * 100 rounded to one decimal, null for no eligible tasks. health = EMPTY when no noncancelled tasks, ATTENTION when any open task is overdue or unassigned, otherwise ON_TRACK. This is task operational health, not an overall financial/business score. overdueItems are the first 5 ordered dueAt/id ascending, exposing only id,title,status,priority,progressPercent,dueAt; overdueHasMore indicates truncation.
- departments (department:read): `{total,active,inactive,items,hasMore}`. First 10 departments by id ascending, including inactive. Each `{id,name,status,employeeCount,openTasks}`; employeeCount includes all profiles and is null without employee:read; openTasks is null without task:read. No silent totals from this bounded list.
- employees (employee:read): `{total,active,inactive}` across all organization profiles.
- workload (task:read AND employee:read): `{items,hasMore}`. First 10 employees with open assigned tasks ranked by openTasks descending/id ascending; includes inactive historical assignees, excludes unassigned tasks. Items `{employeeId,displayName,status,openTasks}`. These are assignment counts, not hours, capacity, utilization or performance rankings. Counts follow Task assignee, independent of Task department.
- notifications: `{total,unread}` for the authenticated recipient in this organization only; ACTIVE membership is sufficient, matching Notifications. No other recipient's count is exposed.
- activity (audit:read): `{items,hasMore}` with latest 10 organization audit events ordered createdAt/id descending. Each item exposes only `{id,event,resourceType,resourceId,outcome,createdAt}`; no security metadata, actor contact details, passwords, tokens or prompt/file/comment content. It reuses the existing audit store.

Lists are bounded dashboard previews with hasMore flags; use existing paginated module APIs for exploration. No arbitrary filters, time window, comparison trends or historical workforce inference. generatedAt is the server cutoff within the transaction. Successful reads do not create audit events; permission-denial handling follows the existing authorization-denied taxonomy. Sensitive bodies, query values and credentials are not logged.

No schema/migration or existing API changes. Frontend must bind responses to the organization that initiated the request, discard stale results, clear data on switching/logout, render Vietnamese loading/empty/error/permission states, and never label a failed or forbidden section as zero. Charts must have accessible numeric labels.
